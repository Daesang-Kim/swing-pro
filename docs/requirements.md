# 골프 스윙 자동 촬영 앱 - 요구사양 정리

## 1. 기본 컨셉
- 골프 스윙을 자동으로 인식하여, 스윙 시작 1~2초 전부터 스윙 종료 후 3~5초까지의 구간을 자동으로 녹화·저장하는 앱
- 사용자가 직접 녹화 버튼을 누르지 않아도, 스윙 동작을 감지해 알아서 하이라이트 클립을 만들어주는 것이 핵심 가치

## 2. 모드 구성

### 2-1. 연습장 모드
- 실내/스크린 연습장 등 고정된 위치에서 반복적으로 스윙하는 상황을 가정
- 스윙 인식 → 자동 녹화 → 클립 저장의 기본 플로우

### 2-2. 필드 모드
- 실제 필드(라운딩) 상황을 가정
- 스윙 자동 녹화 기능은 동일하게 적용
- **추가 기능: 퍼팅 거리 측정 (그린 위)**
  - 목적: 롱 디스턴스(핀까지 전체 거리)가 아니라, 그린 위에서의 짧은 퍼팅 거리 측정
  - 방식: 자동 인식이 아닌 **사용자 터치 기반**
    - 그린 쪽으로 카메라를 비추면 바닥(잔디) 평면 인식
    - 사용자가 화면에서 공 위치를 터치 → 3D 좌표 획득
    - 사용자가 화면에서 홀(컵) 위치를 터치 → 3D 좌표 획득
    - 두 좌표 간 실제 거리를 계산해 표시
  - 이 방식을 택한 이유: 공/핀을 AI가 자동 인식하는 방식보다 정확도가 높고 구현 난이도가 낮음 (사용자가 직접 지점을 지정하므로 인식 오류 요인이 적음)
- **추가 기능: 공 궤적 표시 (트레이서)**
  - 스윙 후 공이 날아가는 경로를 영상 위에 선으로 오버레이
  - 방식: 프레임별로 공을 탐지할 수 있는 구간까지는 실제 탐지 좌표로 궤적을 그리고, 이후(탐지 실패/화면 이탈 등으로 더 이상 추적이 안 되는 구간)는 직전까지의 궤적 흐름을 바탕으로 자연스럽게 이어지는 곡선으로 연결
  - 정확한 물리 데이터(런치각/스핀/캐리거리)를 측정하는 것이 아니라, 시각적으로 보기 좋은 궤적을 보여주는 것이 목적

## 3. 핵심 기능 상세

| 기능 | 설명 |
|---|---|
| 스윙 자동 감지 | 카메라 프리뷰 상에서 스윙 동작(백스윙~팔로스루)을 실시간으로 인식 |
| 프리-롤 버퍼링 | 스윙 시작 시점보다 1~2초 앞선 시점부터 저장되도록, 항상 최근 몇 초를 버퍼에 유지 |
| 포스트-롤 녹화 | 스윙 종료(임팩트/피니시) 인식 후 3~5초간 추가 녹화 후 자동 종료 |
| 클립 자동 저장 | 감지된 구간만 잘라서 개별 영상 파일로 저장 |
| 퍼팅 거리 측정 (필드 모드) | 그린 위에서 공/홀 위치를 터치하면 ARKit 기반 hit-testing으로 실제 거리 계산 |
| 스윙 교정 피드백 | 포즈 추정으로 얻은 관절 좌표를 기준으로 백스윙 각도, 어깨 회전량, 임팩트 시 자세 등을 **샷 유형(풀스윙/어프로치)별 이상적 범위**와 비교해 규칙 기반으로 피드백 제공 (온디바이스, 정형화된 문구 방식) |
| 스윙 점수화 | 각 체크포인트(P1~P10)별 기준값 대비 편차를 종합해 스윙 하나당 점수(예: 0~100점)로 환산, 촬영 직후 바로 표시 |

## 4. 저장소 설계

### 4-1. 기본 방향
- 영상 원본은 **클라우드 업로드 없이 기기 로컬에 저장** (시스템 사진 라이브러리/카메라롤에 저장하는 방식을 전제)
  - 이 경우 저장 공간 관리는 OS가 담당(사용자가 사진 앱에서 직접 정리) — 앱이 별도로 관리할 필요 없음
  - 다만 영상을 일반 파일 경로가 아닌 시스템 라이브러리의 자산 식별자로 참조하게 됨 (iOS: PHAsset identifier / Android: MediaStore URI) — 아래 스키마의 `video_path`는 이 식별자를 저장하는 용도로 사용
- 분석 결과·메타데이터는 **로컬 구조화 DB**(예: SQLite, iOS는 Core Data, Android는 Room 등)에 저장하고, 영상 자산 식별자와 ID로 연결
- 즉, "영상(시스템 사진 라이브러리)" + "분석 데이터(로컬 DB)" 두 축을 분리하되, 클립 ID를 키로 서로 연결하는 구조

### 4-2. 저장해야 할 정보 (엔티티별)

| 엔티티 | 주요 필드 | 비고 |
|---|---|---|
| 사용자 | 사용자ID, 닉네임, 가입일 | (선택) 신체정보 등 |
| 세션 | 세션ID, 사용자ID, 모드(연습장/필드), 시작·종료시각 | 필드모드는 골프장/홀 정보 선택적 확장 |
| 스윙 클립 | 클립ID, 세션ID, 촬영시각, **로컬 영상 파일 경로**, 영상 길이, (선택)클럽 태그 | 영상 원본은 여기서 경로로만 참조 |
| 포즈/스윙 분석 데이터 | 클립ID(FK), 구간별(P1~P10) 관절 각도 요약값, 각 구간의 영상 내 타임스탬프 | **결정: 원본 프레임 좌표 전체가 아닌 구간별 요약값으로 저장** (용량 절약, 재분석은 하지 않는 방향) |
| 스윙 교정 피드백 | 클립ID(FK), 벗어난 항목, 피드백 문구, 생성시각 | 클립별로 1건 이상, 시계열 조회 가능하게 |
| 퍼팅 거리 측정 기록 | 기록ID, 세션ID, 측정시각, 측정거리 | 필드모드 |
| 공 궤적 데이터 | 클립ID(FK), 궤적 좌표 시퀀스, 탐지종료지점 | 필드모드, 있는 경우만 |

### 4-3. UI 개념 — 분석 피드
- 클립(스윙) 단위로 "영상 + 분석 결과"를 한 화면에서 함께 보여주는 상세 뷰 필요
  - 영상 하단에 구간(P1~P10) 탭/마커를 표시하고, 사용자가 터치하면 해당 시점으로 영상이 이동하면서 그 구간의 각도 요약값·피드백이 함께 표시되는 구조
- 전체 클립들을 시간순으로 나열하는 **피드형 목록 화면**에서 각 항목을 탭하면 해당 클립의 상세(영상+구간별 분석) 화면으로 진입하는 구조
- 피드 목록 화면에는 클립별 핵심 요약 정보(촬영일시, 모드, 주요 피드백 한 줄 요약 등)를 카드 형태로 노출하면 좋을 것 같음

## 5. UI/UX 흐름

전체 화면 흐름: **모드 선택 → (연습장 모드 / 필드 모드) → (자동 저장 시 바로 / 확인 후 저장 시 미리보기 확인) → 분석 피드 → 클립 상세**

- **모드 선택**: 앱 진입 시 첫 화면. 연습장 모드 / 필드 모드 두 개의 큰 버튼(또는 카드)으로 단순하게 구성
- **연습장 모드 화면**: 카메라 프리뷰 + 스윙 자동 감지 상태 인디케이터(대기 중/감지됨 등) 위주의 단순한 촬영 화면 + 풀스윙/어프로치 선택 토글, 촬영 방향(정면/후면-다운더라인) 선택(교정 피드백 기준 결정용)
- **필드 모드 화면**: 연습장 모드와 동일한 스윙 자동 촬영 기능(풀스윙/어프로치 선택 포함) + 퍼팅 거리 측정 모드로 전환하는 토글/버튼. 퍼팅 모드에서는 공/홀 터치 UI가 카메라 화면 위에 오버레이됨
- **저장 확인 화면 (설정이 '확인 후 저장'일 때만)**: 스윙 감지 직후 짧은 미리보기와 함께 저장/삭제 버튼 표시
- **분석 피드 화면**: 촬영된 모든 클립을 시간순 카드 리스트로 노출. 카드에는 썸네일, 촬영일시, 모드, 점수, 핵심 피드백 한 줄 요약 등이 들어감
- **클립 상세 화면**: 영상 플레이어 + 하단 구간 마커(P1~P10)로 구성. 마커 탭 시 해당 시점으로 이동하며 그 구간의 각도값·피드백이 함께 표시. 상단에 종합 점수 노출
- **설정 화면**: 스윙 클립 저장 방식(자동 저장 / 확인 후 저장), 촬영 방향 감지 방식(자동 감지 / 직접 선택) 등을 변경하는 메뉴

**관계 요약**
- `users` 1 — N `sessions`
- `sessions` 1 — N `swing_clips`, 1 — N `putting_measurements`

- `swing_feedback` 계산 시 `swing_clips.shot_type` + `swing_clips.camera_view` + `swing_pose_segments.segment_type` 기준으로 `swing_reference_ranges`에서 해당 기준값을 조회해 비교

**결정이 필요한 부분**
- `angle_summary`, `detected_points` 같은 구조화 데이터를 JSON 컬럼(TEXT로 직렬화)으로 둘지, 별도 정규화 테이블로 쪼갤지 — 우선은 JSON 컬럼으로 단순화하는 걸 제안드려요 (조회 패턴이 "클립 하나 통째로 불러오기" 위주라면 충분)

## 7. 참고: 기술적으로 고려해볼 지점 (검토용, 논의 필요)

이 부분은 요구사양이라기보다 구현 방식 논의를 위한 메모입니다. 필요 없으면 지우셔도 됩니다.

1. **스윙 인식 방식 — 포즈 추정 기반으로 결정**
   - 사람 관절(어깨, 팔, 손목 등) 위치를 온디바이스 컴퓨터 비전 모델로 실시간 추적해 백스윙~임팩트~피니시 패턴을 인식
   - iOS: Apple Vision 프레임워크(Body Pose Detection) / Core ML, Android: ML Kit 또는 MediaPipe 활용 — 모두 기기 내에서 로컬 실행되며 별도 서버 호출·토큰 과금 없음

2. **프리-롤 버퍼링 구현**
   - 상시 촬영 중 최근 N초를 순환 버퍼(circular buffer)에 유지하다가, 스윙 감지 시점에 버퍼 시작 지점부터 저장 시작 — iOS/Android 모두 관련 카메라 API로 구현 가능한 패턴

3. **퍼팅 거리 측정 (그린 위, 터치 기반)**
   - ARKit의 평면 인식(그린 바닥 평면 인식) + 화면 터치 지점을 3D 좌표로 변환하는 hit-testing 기능을 조합해 구현
   - 공/핀을 AI가 자동으로 찾는 방식이 아니라 사용자가 직접 터치로 지정하므로, 객체 인식 모델 없이도 구현 가능하고 정확도도 상대적으로 높음
   - LiDAR 탑재 기기는 더 정밀하지만, 없는 기기도 근거리(그린 위 퍼팅 거리 수준)에서는 Visual-Inertial Odometry 방식으로 어느 정도 정확한 측정 가능
   - 고려사항: 터치 정확도 보정 UX(확대/드래그 미세조정), 평면 인식 실패 시 예외 처리, 카메라 각도 가이드

4. **공 궤적 표시 (트레이서)**
   - 프레임별 공 탐지(배경 대비 밝기/색상 차이, 프레임 간 차분 등)로 실제 궤적을 그리다가, 탐지가 끊기는 시점부터는 직전 궤적의 방향/곡률을 바탕으로 자연스럽게 이어지는 곡선을 그려 연결
   - 정확한 탐지가 필요한 구간(초반 임팩트 직후)만 잘 잡아내면 되므로, 전체 비행 구간을 끝까지 추적하는 것보다 구현 부담이 적음
   - 고프레임레이트 촬영(120~240fps 권장)이 뒷받침되어야 탐지 정확도가 확보됨

5. **성능/배터리**
   - 상시 카메라 프리뷰 + 실시간 포즈 추정은 배터리/발열 부담이 큼 → 온디바이스 경량 모델 사용, 프레임레이트 조절 등 고려 필요

6. **플랫폼 — iOS 네이티브로 우선 진행**
   - 스윙 인식(Vision), 퍼팅 거리 측정(ARKit), 영상 저장(Photos) 등 핵심 기능이 Apple 프레임워크에 깊게 의존 → 크로스플랫폼 프레임워크를 쓰더라도 결국 네이티브 모듈이 필요해 이점이 적음
   - **결정: iOS 네이티브(Swift)로 먼저 개발**, 안드로이드는 추후 별도 네이티브 포팅을 염두에 두고 설계 (자세한 내용은 9장 기술 스택 참고)

7. **스윙 교정 피드백 (1단계, 규칙 기반)**
   - 포즈 추정으로 얻은 프레임별 관절 좌표에서 P1~P10 각 체크포인트의 주요 각도 지표(어깨 회전량, 척추/상체 각도 등)를 계산
   - **결정: 풀스윙과 어프로치를 구분해서 분석** — 두 샷 유형은 스윙 크기와 동작 패턴 자체가 달라 같은 기준으로 비교하면 부정확한 피드백이 나올 수 있음
   - 클립의 `shot_type`(풀스윙/어프로치)과 구간별 기준값(`swing_reference_ranges`)을 조회해 비교, 벗어난 항목에 대해 미리 준비된 템플릿 문구로 피드백 제공
   - 클럽 종류(드라이버/아이언/웨지 등)별 세분화는 초기 범위에서는 제외 — 데이터가 쌓이면 추후 확장 검토
   - LLM 등 생성형 AI 없이 규칙 기반 로직만으로 구현 — 온디바이스, 토큰 과금 없음
   - (참고: 자연어로 더 유연하게 코칭해주는 2단계는 이번 범위에서 제외, 추후 필요 시 LLM 연동 검토 가능)

8. **촬영 방향 (정면 / 다운더라인) — 자동 감지 + 수동 보정**
   - 같은 관절 각도라도 정면(face-on)에서 찍은 영상과 후면(down-the-line)에서 찍은 영상은 카메라 기준 각도 해석이 달라짐 — 어떤 지표를 어느 방향에서 정확히 잴 수 있는지도 달라질 수 있음
   - **1차: 자동 감지** — 어드레스(P1) 시점의 골격 형태(어깨/골반 폭의 좌우 대칭성, 폭 비율 등)로 방향을 규칙 기반으로 추정. 무거운 별도 모델 없이 기존 포즈 추정 결과만으로 계산 가능
   - **2차: 수동 보정** — 자동 감지 신뢰도가 낮거나 사용자가 설정에서 '직접 선택'을 택한 경우, 화면에서 방향을 직접 지정
   - 이 값을 기준값 비교(`swing_reference_ranges`) 조회에 함께 사용

9. **스윙 점수화**
   - 각 체크포인트(P1~P10)에서 계산된 지표들이 기준 범위(`swing_reference_ranges`)에서 얼마나 벗어났는지를 종합해 하나의 점수(예: 0~100점)로 환산
   - 규칙 기반 가중 평균 방식으로 구현 — 예: 핵심 체크포인트(P4, P7 등)에 가중치를 더 주는 방식 고려 가능
   - 스윙 교정 피드백과 마찬가지로 온디바이스 규칙 기반 계산, LLM 불필요 — 촬영 직후 바로 점수 표시 가능

## 8. 향후 고려사항 (초기 범위 제외, 추후 검토)

- **개인화**: 현재 교정 기준값(`swing_reference_ranges`)은 샷 유형·촬영 방향 기준의 고정값. 신체 정보(키, 팔 길이 등)에 따른 사용자별 보정 계수는 초기 범위에서 제외, 추후 확장 검토
- **트렌드/추이 화면**: 현재 분석 피드는 클립 단위 조회 구조. "특정 지표가 시간이 지나며 어떻게 변하는지"를 보여주는 시계열 추이 화면(또는 탭)은 이번 범위에서 제외, 추후 추가 검토
- **프라이버시**: 필드 모드 촬영 시 주변 다른 사람이 화면에 함께 촬영될 수 있음. 현재는 로컬 저장이라 리스크가 크지 않지만, 이후 공유 기능을 실제로 구현할 때 한 번 짚고 갈 필요 있음

## 9. 기술 스택

**결정: iOS 네이티브로 우선 개발.** 스윙 인식(포즈 추정), 퍼팅 거리 측정(평면 인식·hit-testing), 영상 저장 등 핵심 기능이 OS 프레임워크에 깊게 의존하는 구조라, 크로스플랫폼 프레임워크를 쓰더라도 결국 네이티브 모듈이 필요해 이점이 적음. 안드로이드는 추후 별도 네이티브로 확장하는 것을 염두에 두고, 아래처럼 기능-프레임워크 대응 관계를 미리 정리해둠.

| 기능 | iOS (1차 개발) | Android (추후 확장) |
|---|---|---|
| 언어/UI | Swift + SwiftUI | Kotlin + Jetpack Compose |
| 카메라/프리롤 버퍼링 | AVFoundation | CameraX |
| 스윙 인식(포즈 추정) | Vision 프레임워크 (Body Pose) | ML Kit Pose Detection 또는 MediaPipe |
| 퍼팅 거리 측정(평면 인식·hit-testing) | ARKit | ARCore |
| 공 궤적 탐지 | Vision / Core ML | MediaPipe / TensorFlow Lite |
| 영상 저장 | Photos 프레임워크 (PHAsset) | MediaStore API |
| 로컬 DB | Core Data 또는 GRDB(SQLite) | Room (SQLite) |

**확장 시 고려할 점**
- 안드로이드는 iOS만큼 LiDAR 탑재 기기가 흔하지 않아, 퍼팅 거리 측정 정확도가 기기별로 iOS보다 편차가 클 수 있음 — 확장 시 별도 검증 필요
- 로직(스윙 판별 규칙, 점수 계산식, 기준값 비교 등)은 플랫폼 독립적으로 설계해두면, 추후 안드로이드로 포팅할 때 알고리즘을 그대로 재사용하고 프레임워크 연동 부분만 새로 작성하면 됨
